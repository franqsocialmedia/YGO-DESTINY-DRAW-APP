INFORMACIÓN GENERAL DEL PROYECTO
--------------------------------------------------------------------------------
Nombre: Destiny Draw - Yu-Gi-Oh! App
Plataforma: Web (HTML5, CSS3, JavaScript)
Prioridad: Mobile-First (responsive para PC)
Funciona: SIN SERVIDOR LOCAL (solo necesita un navegador)
Inicio del Proyecto: 07/02/2025
Última Actualización: 07/02/2025 - v1.2.0

OBJETIVO DEL PROYECTO
--------------------------------------------------------------------------------
Crear una aplicación web llamada "Destiny Draw" funcional y sencilla para 
gestionar mazos (decks) de Yu-Gi-Oh!, con capacidades de búsqueda de cartas, 
análisis estadístico, simuladores, información del meta actual, recursos de 
formación y configuración personalizable.

La aplicación está diseñada con arquitectura modular para facilitar el
mantenimiento y escalabilidad futura.

CARACTERÍSTICA CLAVE: Funciona completamente SIN SERVIDOR
- Solo se necesita abrir index.html en cualquier navegador
- La API de YGOPRODeck permite CORS, no requiere backend
- Todos los módulos funcionan client-side

PALETA DE COLORES PRINCIPAL
--------------------------------------------------------------------------------
Color Base: #003366 (Azul marino oscuro)
El esquema de colores está diseñado alrededor de este tono azul profundo,
que da una sensación profesional y relacionada con el tema de Yu-Gi-Oh!

Colores completos:
- Primary: #003366 (Azul marino oscuro - BASE)
- Secondary: #004080 (Azul marino medio)
- Accent: #0066cc (Azul brillante)
- Gold: #FFD700 (Dorado - Yu-Gi-Oh!)
- Background Dark: #001a33
- Background Card: #002b4d
- Text Light: #f1f1f1

API UTILIZADA - YGOPRODECK
--------------------------------------------------------------------------------

URL Base: https://db.ygoprodeck.com/api/v7/cardinfo.php

Parámetros:
- fname: Fuzzy name search (búsqueda parcial por nombre)
- name: Exact name search
- type: Tipo de carta
- race: Raza
- attribute: Atributo
- level: Nivel
- etc.

Ejemplo:
https://db.ygoprodeck.com/api/v7/cardinfo.php?fname=dark

IMPORTANTE: 
- Esta API permite CORS
- No requiere API key
- Funciona sin servidor
- Gratis para uso público

Respuesta JSON:
{
  "data": [
    {
      "id": 12345,
      "name": "Dark Magician",
      "type": "Normal Monster",
      "desc": "...",
      "atk": 2500,
      "def": 2100,
      "level": 7,
      "race": "Spellcaster",
      "attribute": "DARK",
      "card_images": [
        {
          "image_url": "...",
          "image_url_small": "..."
        }
      ]
    }
  ]
}

6. Comentarios completos:
   Razón: Código auto-documentado para futuros desarrolladores
   
7. Botón amarillo con opacity 0.7:
   Razón: Visible pero no intrusivo, contrasta con azul

NOTAS PARA DESARROLLADORES
================================================================================

CÓMO AGREGAR UN NUEVO MÓDULO:

1. Crear archivo CSS en css/ con prefijo "style_"
2. Crear archivo JS en Modules/ (si requiere lógica)
3. Agregar <link> al CSS en index.html
4. Agregar <script> al JS en index.html
5. Crear sección HTML con id="nombremodulo-content"
6. Agregar botón en navegación con data-tab="nombremodulo"
7. Agregar nombre del tab al array Navigation.tabs
8. Integrar Logger.functionStart/End
9. Documentar en Report.txt

CÓMO USAR EL LOGGER:

```javascript
// Al inicio de función
Logger.functionStart('NombreMódulo', 'nombreFunción');

// Info general
Logger.info('NombreMódulo', 'Mensaje', datosOpcionales);

// Errores
Logger.error('NombreMódulo', 'Error', errorObject);

// Click de botón
Logger.buttonClick('button-id', 'Texto', 'NombreMódulo');

// Al final de función
Logger.functionEnd('NombreMódulo', 'nombreFunción', resultadoOpcional);
```

TESTING:

1. Abrir index.html en navegador
2. Abrir consola (F12)
3. Ver logs de inicialización
4. Probar cada funcionalidad
5. Verificar que no hay errores en consola

DEPLOYMENT:

Para producción:
1. Minificar CSS y JavaScript (opcional)
2. Optimizar imágenes
3. Subir a hosting estático (GitHub Pages, Netlify, etc.)
4. ¡No se necesita servidor!

- CORRECCIÓN DE EXPORTACIÓN .YDK

Se corrigió un error crítico en la función exportYDK() que causaba que todas las cartas se exportaran a 1 copia independientemente de la cantidad real.

Problema identificado:
- El formato .ydk requiere repetir el ID de cada carta tantas veces como copias tenga
- La versión anterior solo escribía cada ID una vez

Solución implementada:
```javascript
Object.entries(this.cards).forEach(([id, item]) => {
    // Repetir el ID tantas veces como copias tenga
    for (let i = 0; i < item.qty; i++) {
        if (item.location === 'main') main += id + '\n';
        if (item.location === 'extra') extra += id + '\n';
        if (item.location === 'side') side += id + '\n';
    }
});
```

Estructura del archivo .ydk:
#created by Destiny Draw
#main
[IDs del Main Deck, repetidos según cantidad]
#extra
[IDs del Extra Deck, repetidos según cantidad]
!side
[IDs del Side Deck, repetidos según cantidad]

1. ARQUITECTURA DEL MÓDULO DE ESTADÍSTICAS (estadisticas.js)
Se ha implementado el módulo Estadisticas bajo un patrón de objeto literal (Singleton), centralizando la lógica de análisis comparativo entre el deck del usuario y el "Meta".


Persistencia Local (LocalStorage): * El sistema utiliza la clave yugioh_meta_decks para almacenar toda la estructura de carpetas y decks sin necesidad de base de datos externa.


Por qué: Permite que el usuario mantenga su base de datos de consulta de forma privada y ultrarrápida.

Sistema de Carpetas Cronológicas:

Los decks se organizan en "Folders" (ej: "Febrero 2026").

Incluye lógica de ordenamiento por fecha (getMonthNumber) para que las carpetas más recientes aparezcan siempre primero.

2. MOTOR DE PROCESAMIENTO Y PARSING (YDK)
A diferencia del buscador que usa API, el módulo de estadísticas procesa archivos locales:


Parser de Archivos .ydk: Implementa parseYDK que limpia y extrae IDs de cartas directamente de archivos de texto del juego.


Identificación Automática de Miniaturas: * Función getMostFrequentCardId: Analiza el deck importado y determina cuál es la carta más repetida.


Cómo funciona: Este ID se usa para consultar automáticamente la imagen en los servidores de YGOPRODeck, asignando un arte representativo al deck de forma dinámica.

3. COMPONENTES DE INTERFAZ AVANZADOS (UI/UX)
Se han añadido elementos visuales críticos detallados en style_estadisticas.css:


Deck Floating Widget: * Un componente flotante que permite al usuario previsualizar el deck activo mientras navega por las estadísticas.

Visualización de Scores Mediante Barras:

Se implementó un sistema de barras de progreso dinámicas (.stat-bar) con transiciones CSS para representar la Consistencia, Potencia y Resiliencia.

Utiliza colores variables (Dorado/Azul) para indicar la calidad del deck respecto al estándar de competición.

4. MEJORAS DE NAVEGACIÓN Y FEEDBACK

Fallback de Imágenes: Se implementó lógica de onerror en los thumbnails de los decks para mostrar una imagen por defecto (placeholder) si la API falla o la carta no existe, evitando "broken images" en la interfaz.


Animaciones de Entrada: El contenido de estadísticas carga con una animación fadeIn de 0.4s para suavizar la transición entre módulos.


Filtrado Dinámico: El usuario puede filtrar la vista de decks por carpeta sin recargar la página (setFolderFilter), optimizando la gestión de grandes volúmenes de datos.

RAZÓN DE ESTOS CAMBIOS:

NOTAS TÉCNICAS ADICIONALES PARA PROGRAMADORES:

Importación Masiva: El método importYDK soporta la selección múltiple de archivos mediante input.multiple = true, procesándolos de forma asíncrona con Promise.all para no bloquear el hilo principal de la UI.

Los elementos `.widget-deck-item / .meta-deck-item` del widget:

* Son creados dinámicamente mediante `innerHTML`
* No poseen eventos `click` activos después del render
* No existe **delegación de eventos** en el contenedor padre

Cada re-render del widget elimina cualquier listener previamente asociado a los items.

---

## 3. DECISIÓN TÉCNICA

Se descartó:

* Uso de `onclick` inline
* Re-asignación de eventos por item tras cada render

Se adoptó:

* **Delegación de eventos** desde el contenedor del widget

Esta solución:

* Es persistente
* No depende del ciclo de render
* Escala correctamente con filtros, carpetas y futuros cambios

---

## 4. CAMBIOS IMPLEMENTADOS

### 4.1 Nuevo Listener Global del Widget

Se añadió un único listener `click` al contenedor `.deck-floating-widget`.

#### Función añadida

```js
Estadisticas.initFloatingDeckWidgetEvents()
```

Responsabilidades:

* Detectar clicks en cualquier deck renderizado
* Ignorar clicks en botones secundarios (eliminar)
* Extraer `data-deck-id`
* Delegar la acción de carga del deck

---

### 4.2 Lógica de Apertura / Sustitución de Deck

Se añadió / reemplazó la función responsable de cargar el deck desde el widget.

#### Función utilizada

```js
Estadisticas.openDeckFromWidget(deckId)
```

Responsabilidades:

* Buscar el deck seleccionado en `localStorage`
* Sustituir el deck activo (`Deck.cards`)
* Actualizar el nombre del deck (`Deck.name`)
* Renderizar el nuevo estado
* Marcar visualmente el deck activo

---

## 5. INTEGRACIÓN EN EL CICLO DE VIDA

La inicialización del listener se ejecuta:

* Una sola vez
* Después del render del widget
* Preferentemente desde `init()` o al final de `renderFloatingWidget()`

```js
Estadisticas.initFloatingDeckWidgetEvents();
```

Esto garantiza que:

* El listener no se duplique
* No se pierda tras futuros renders

Esa es la idea general. Necesitaria que crees este primer paso. Pero si hay alguna mejor sugerencia o forma de abordar la meta de este paso, puedes compartilo. Pero toma en cuenta la existencia de los siguientes pasos para que sepas a donde se dirigira todo esto. PD: El ecosistema de cartas registrados le llamaremos: Cartas META (Most Efficient Strategy Available o algo asi). El meta depende de que hayan otras cartas a las cuales ser counter o aportar. Por todo esto, el sistema de counter sera aparte del de la carta asi como lo es especialidad y roles (los roles son los unicos que se marcaran visiblemente como ya lo hace como tags pero especialidad y counter seran datos internos no publicos)  *por ejemplo que hayan palabras clave como "return" es "Recycle" como rol, pero en sí mismo, "return" en el deck aumenta de nivel. generando que cuando un deck tiene muchas cartas con esa palabra clave significa que la especialidad del deck es bounce, y asi sucesivamente con otros nombres que luego te dare. Pero la especializacion es sobre el deck y el Rol es sobre la carta. En configuracion quiero una seccion donde pueda agregar otras palabras clave que seran tomadas en cuenta como especializaciones para cartas y el nombre que recibe al ser para un deck (por defecto dira lo mismo que para la carta).

Quiero que internamente haya una lista de staples (cartas genericas) que yo mismo introducire, aunque quiero que empieces con estas como ejemplo: "Renace al monstruo", "tifon mistico espacial" y "fuerza del espejo". Esta lista no se mostrara visualmente, estara interno en el sistema y dicha lista puede ser ampliada, editada o eliminada desde configuraciones. Debe de aplicarse Roles, especialidad y counters.

Paso 3: Ajustar roles compuestos. Se trata de poder poner no solo palabra clave que posea X o Y rol, sino que tambien haya una lista de palabras clave que se tomen como condicionales, para que solo tome en cuenta el rol si cumple dicha condicional y 1 o mas de las palabras claves del rol. Ej.: "Quick-Effect" (condicional) y "from your hand", "from the hand", "from theirs hands", etc. (con cumplir alguna de estas + la condicional entonces es considerado el rol correspondiente). Si no posee condicional (si se deja en blanco) entonces es porque ese rol no tiene condicionales.

Paso 4: Nomenclatura de cartas, esto sera otro modulo. Es la funcion o modulo que debe de desglosar lo que posee o no posee la carta (velocidad de efecto, tipo de efecto, timming del efecto, si posee o no requisitos, condiciones, costos, efectos/objetivos (con su conectores logicos), duracion y restriccion). Paso 5: Cada carta en el META debe ser contado (incluyendo sus copias) para establecer un nivel de recurrencia de dicha carta, asi vemos cuales son las cartas que mas se usan. Tambien debe mostrar un promedio de a cuantas copias se suele llevar por deck. Esto debe ser en el mismo modulo que se esta trabajando los Internal Score y External Score.

Paso 6: Debe crearse una funcion como sistema de puntos de poder para cada carta individual. Esto se multiplica por copia, y este nivel de poder debe ser siguiendo la logica de: Una carta usada mucho en el META actual, se usa porque es muy util por ello sus puntos deben ser altos, gracias a que es una gran especializacion para la mayoria de (cartas y decks en el Meta) o porque le aumentan la especialidad que ya tenian los decks actuales. Digamos que le da un puesto por uso (digamos, por utilidad). Pero sea cual sea la razon, si existe una carta counter en el meta, dicha counter debe aumentar su poder segun a los rangos de las cartas a las que les hace counter, porque su relevancia se incrementa y detiene a mas cartas y mas decks por su alta concurrencia. Esa es la logica detras de los puntos de poder por cartas. Que supongo que como esto nace de una comparativa con otras cartas, al igual que los counters dependen del meta por eso sera algo que ira ajustandose segun los decks que hay en el meta.

Paso 7: El sistema de counter los dividiremos en Counter-cards y counter-decks. El primero es el nivel counter que posee cada carta por separado y el segundo es el nivel de counter que posee el deck por la suma de poder counter de todas las cartas que posee. Tomar en cuenta que habran roles que disminuyen el poder counter-deck. Como que Brick disminuye el poder counter en general.

Paso 8: Sistema de analisis del deck. Es una seccion especial donde tomara el deck completo y dara respuestas pre-establecidas segun las estadisticas del mismo. Ejemplo: El Deck X posee un poder teórico de 7/10 puntos de poder (que viene de los internal score del Deck), pero frente al META es de 3/10 (puntos externos) por la existencia de decks como X, Y y Z (que son counters-decks). Cartas como : A y B podrían ayudar en este formato actual (cartas staples que son counters de los counters del deck)

Paso 9: Poder exportar los datos del deck, del meta, staples y demas funciones que necesitan ser ajustadas para poder usarlos para analisis de parte de los jugadores.

CONCEPTO - ROLES COMPUESTOS
================================================================================

ROLES SIMPLES (Paso 1):
- Solo verifica que AL MENOS UNA keyword esté presente
- Ejemplo: "Searcher" → ["add", "from your deck"]
- Si encuentra "add" → asigna rol Searcher

ROLES COMPUESTOS (Paso 3):
- Verifica que TODAS las condicionales estén presentes
- Y que AL MENOS UNA keyword esté presente
- Ejemplo: "Handtrap" → 
  • Condicionales: ["quick-effect"] (DEBE estar)
  • Keywords: ["from your hand", "from the hand"] (AL MENOS UNA)
- Si tiene "quick-effect" Y "from your hand" → asigna rol Handtrap

BENEFICIO:
- Mayor precisión en detección de roles
- Evita falsos positivos
- Permite roles más específicos y complejos

1. DECK.JS - autoAssignRoles()
--------------------------------------------------------------------------------

LÓGICA ACTUALIZADA:

Para cada rol:
1. Verificar si existe en roleConditions
2. Si existe en roleConditions:
   a) Verificar que TODAS las condicionales estén en desc
   b) Si todas las condicionales se cumplen:
      - Verificar que AL MENOS UNA keyword esté en desc
      - Si se cumple → asignar rol
3. Si NO existe en roleConditions:
   - Usar lógica simple (buscar keywords en roles)
   - Si encuentra alguna → asignar rol

PSEUDOCÓDIGO:
```javascript
for each (roleName, keywords) in roles {
  if (roleConditions[roleName]) {
    // ROL COMPUESTO
    allConditionsMet = true
    for each conditional in roleConditions[roleName].conditionals {
      if (!desc.includes(conditional)) {
        allConditionsMet = false
        break
      }
    }
    
    if (allConditionsMet) {
      for each keyword in roleConditions[roleName].keywords {
        if (desc.includes(keyword)) {
          assignRole(roleName)
          break
        }
      }
    }
  } else {
    // ROL SIMPLE
    for each keyword in keywords {
      if (desc.includes(keyword)) {
        assignRole(roleName)
        break
      }
    }
  }
}
```

VENTAJAS:
- Compatible con roles simples (sin romper nada)
- Permite roles complejos y precisos
- Escalable y mantenible

PRÓXIMO PASO:
Implementar Paso 5 - Sistema de recurrencia y análisis de uso de cartas en el META

================================================================================

Este paso 4 tuvo que dividirse en 2 partes donde la segunda parte fue la siguiente peticion:

Quiero que al ver una carta (en el panel flotante) en el texto se subraye las parte del efecto (segun la nomenclatura de las cartas, y estas a su vez serán definidas, editadas o eliminadas en config. también quiero poder elegir un color para cada parte de la nomenclatura de las cartas) y que ese subrayar sea con una especie de mark del color definido para dicha parte de la nomenclatura (un mark con transparencia 0.6). Aunque no todas las cartas cubren todas las partes de la nomenclatura.

La nomenclatura general es la siguiente: 

Velocidad de hechizo. Solo puede ser 1, son: Velocidad 1 (cuando no posee nada de las demas velocidades o cuando posee "You can" iniciando en mayuscula), Velocidad 2 (cuando poseen: "When" o "If" iniciando en mayusculas en la condicion de activacion, tambien si es una carta del tipo "spell" y del subtipo: "quick-play" o si es una carta del tipo "trap" que no sea del subtipo: "counter"), Velocidad 3 (cuando la carta es especificamente tipo: "trap" y subtipo: "counter") y Irrespondible (cuando la carta expresa "in response to this card's activation"). Siempre se pone solo la velocidad mas alta en caso de cumplir con 2 o mas.



Timming del efecto. En respuesta (si tiene "when"), Siguiente cadena (si tiene "If"), En resolucion (cuando tiene "instead" o "resolves"), Inmediatamente (cuando tiene "immediatly"), Por cada uno (cuando tiene "each time") o Al activar/invocar (si no cumple ninguno de los requisitos de Timming anteriormente mencionados). Este Timming del efecto es 1 por efecto, asi que seria el timming del efecto 1, 2, etc. 



Requisitos. Son los recursos que necesita la carta para poder activar en principio sino seria una jugada ilegal. Ej.: Si una carta tiene el efecto donde dice: "send this card from your hand to the GY..." es porque el requisito es tenerlo en mano y poder enviar cartas al cementerio. O si una carta dice: "special summon 1 monster from your deck..." es porque debe haber minimo 1 carta tipo monstruo en el deck. Asi es la logica de esta parte. Obviamente tiene que ser algo mas simple a nivel de automatizacion por palabras clave. El como resolver esto, me dejas saber e implementalo mientras.



Condicion de activacion. Ya esto es mas especifico del como esta escrito una carta (hay cartas que poseen esto y otras no. En los casos de no tenerlo se pone que NO posee Condicion de activacion o cualquiera de los siguientes puntos). Las cartas para esta parte se lee por oraciones completas (no palabras por separado, ignorando las , coma como divisor de oraciones) y se ve como acaba cada oracion. La condicion de activacion son las oraciones que acaban en : (dos puntos). Tambien son las oraciones que inician en When o If terminando en : (dos puntos).



Costo de activacion. El costo de activacion son las oraciones que acaban en ; (punto y coma)



Efecto 1. Los efectos son todas la oraciones que acaba en . mientras no posea la palabra clave "follow" o no hayan podido cumplir ninguna de los puntos anteriores ni siguientes.



Tipo de efecto 1. Son efectos Mandatory cuando luego del costo de activacion o la condicion lo que sigue es el efecto 1 y no inicia el efecto con la palabra clave "you can". Trigger, son los tipos de efectos que se activan por ser el Timming de activacion: En respuesta. Estan los Quick Effect, son los tipos de efectos que poseen "Quick Effect" en la condicion. Tambien estan los Ignition, que son los tipos de efectos que no cumple ninguna de las anteriores categorias de tipo de efecto. Aunque tomar en cuenta que Mandatory  puede estar combinada con Ignition y con Trigger, siendo asi: Ignition-Mandatory o Trigger-Mandatory, respectivamente. Los Mandatory sin condiciones ni costos son conocidos como efectos Continuos.



Efecto 2. Es lo mismo que Efecto 1 solo que es en otra oracion posterior que cumpla los requisitos para ser efecto. Pudiendo haber mas de 2 efectos.



Tipo de efecto 2. Esto sera igual para cada efecto. 



Duracion del efecto. son las oraciones que poseen "for the rest", "phase of this turn", "phase of the next turn", "phase of the next opponent's turn", "phase of your next turn", "During your", "During the"



Restriccion o lock. Son las oraciones donde termina con . pero tiene la palabra clave "you cannot"



Limitacion. Son las oraciones que poseen alguna de las siguientes palabras clave "per turn", "per duel" o "you can only use" o "you can only activate"

--------------------------------------------------------------------------------

ANTES (Arrays de keywords):
```javascript
effectSpeed: {

    "Trigger": ["when", "if"]

```

DESPUÉS (Objetos con 4 campos):
```javascript
effectSpeed: {
    "Quick Effect": {
        start: "quick effect",      // Palabra de inicio
        internal1: "",               // Primera palabra interna
        internal2: "",               // Segunda palabra interna
        end: ":"                     // Palabra/signo de fin
    },
    "Trigger": {
        start: "when",
        internal1: "",
        internal2: "",
        end: ":"
    }
}
```

SIGNIFICADO DE LOS CAMPOS:
- **start**: Palabra clave que debe aparecer al INICIO del párrafo
- **internal1**: Primera palabra que debe estar DENTRO del párrafo
- **internal2**: Segunda palabra que debe estar DENTRO del párrafo  
- **end**: Palabra o signo de puntuación que debe aparecer al FINAL

CAMPOS VACÍOS:
- Si un campo está vacío (""), NO se verifica
- Permite flexibilidad: algunas configuraciones solo necesitan 1-2 campos
- Ejemplo: Solo internal1 + end, sin start ni internal2

PROBLEMAS CONOCIDOS Y SOLUCIONES
================================================================================

1. PROBLEMA: Imágenes en blanco en PNG descargado
   CAUSA: CORS (Cross-Origin Resource Sharing)
   SOLUCIÓN: Ver SOLUCION_CORS_DECKLIST.txt
   OPCIONES:
   - Extensión CORS en navegador (más fácil)
   - Servidor local con proxy
   - Imágenes locales
   - Solo texto sin imágenes

2. PROBLEMA: Widget no muestra imagen
   CAUSA: CSS no cargado
   SOLUCIÓN: Agregar style_widget_thumbnails.css

3. PROBLEMA: Badges amarillos no aparecen
   CAUSA: CSS no cargado
   SOLUCIÓN: Agregar style_subtypes.css
