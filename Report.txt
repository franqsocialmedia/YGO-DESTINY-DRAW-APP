INFORMACIÓN GENERAL DEL PROYECTO
--------------------------------------------------------------------------------
Nombre: Destiny Draw - Yu-Gi-Oh! App
Plataforma: Web (HTML5, CSS3, JavaScript)
Prioridad: Mobile-First (responsive para PC)
Funciona: SIN SERVIDOR LOCAL (solo necesita un navegador)
Inicio del Proyecto: 07/02/2025
Última Actualización: 07/02/2025 - v1.2.0

OBJETIVO DEL PROYECTO
--------------------------------------------------------------------------------
Crear una aplicación web llamada "Destiny Draw" funcional y sencilla para 
gestionar mazos (decks) de Yu-Gi-Oh!, con capacidades de búsqueda de cartas, 
análisis estadístico, simuladores, información del meta actual, recursos de 
formación y configuración personalizable.

La aplicación está diseñada con arquitectura modular para facilitar el
mantenimiento y escalabilidad futura.

CARACTERÍSTICA CLAVE: Funciona completamente SIN SERVIDOR
- Solo se necesita abrir index.html en cualquier navegador
- La API de YGOPRODeck permite CORS, no requiere backend
- Todos los módulos funcionan client-side

PALETA DE COLORES PRINCIPAL
--------------------------------------------------------------------------------
Color Base: #003366 (Azul marino oscuro)
El esquema de colores está diseñado alrededor de este tono azul profundo,
que da una sensación profesional y relacionada con el tema de Yu-Gi-Oh!

Colores completos:
- Primary: #003366 (Azul marino oscuro - BASE)
- Secondary: #004080 (Azul marino medio)
- Accent: #0066cc (Azul brillante)
- Gold: #FFD700 (Dorado - Yu-Gi-Oh!)
- Background Dark: #001a33
- Background Card: #002b4d
- Text Light: #f1f1f1

API UTILIZADA - YGOPRODECK
--------------------------------------------------------------------------------

URL Base: https://db.ygoprodeck.com/api/v7/cardinfo.php

Parámetros:
- fname: Fuzzy name search (búsqueda parcial por nombre)
- name: Exact name search
- type: Tipo de carta
- race: Raza
- attribute: Atributo
- level: Nivel
- etc.

Ejemplo:
https://db.ygoprodeck.com/api/v7/cardinfo.php?fname=dark

IMPORTANTE: 
- Esta API permite CORS
- No requiere API key
- Funciona sin servidor
- Gratis para uso público

Respuesta JSON:
{
  "data": [
    {
      "id": 12345,
      "name": "Dark Magician",
      "type": "Normal Monster",
      "desc": "...",
      "atk": 2500,
      "def": 2100,
      "level": 7,
      "race": "Spellcaster",
      "attribute": "DARK",
      "card_images": [
        {
          "image_url": "...",
          "image_url_small": "..."
        }
      ]
    }
  ]
}

NOTAS PARA DESARROLLADORES

CÓMO AGREGAR UN NUEVO MÓDULO:

1. Crear archivo CSS en css/ con prefijo "style_"
2. Crear archivo JS en Modules/ (si requiere lógica)
3. Agregar <link> al CSS en index.html
4. Agregar <script> al JS en index.html
5. Crear sección HTML con id="nombremodulo-content"
6. Agregar botón en navegación con data-tab="nombremodulo"
7. Agregar nombre del tab al array Navigation.tabs
8. Integrar Logger.functionStart/End
9. Documentar en Report.txt

CÓMO USAR EL LOGGER:

```javascript
// Al inicio de función
Logger.functionStart('NombreMódulo', 'nombreFunción');

// Info general
Logger.info('NombreMódulo', 'Mensaje', datosOpcionales);

// Errores
Logger.error('NombreMódulo', 'Error', errorObject);

// Click de botón
Logger.buttonClick('button-id', 'Texto', 'NombreMódulo');

// Al final de función
Logger.functionEnd('NombreMódulo', 'nombreFunción', resultadoOpcional);
```

3. Ver logs de inicialización
4. Probar cada funcionalidad
5. Verificar que no hay errores en consola

DEPLOYMENT:

Para producción:
1. Minificar CSS y JavaScript (opcional)
2. Optimizar imágenes
3. Subir a hosting estático (GitHub Pages, Netlify, etc.)

- CORRECCIÓN DE EXPORTACIÓN .YDK

Se corrigió un error crítico en la función exportYDK() que causaba que todas las cartas se exportaran a 1 copia independientemente de la cantidad real.

Problema identificado:
- El formato .ydk requiere repetir el ID de cada carta tantas veces como copias tenga
- La versión anterior solo escribía cada ID una vez

Solución implementada:
```javascript
Object.entries(this.cards).forEach(([id, item]) => {
    // Repetir el ID tantas veces como copias tenga
    for (let i = 0; i < item.qty; i++) {
        if (item.location === 'main') main += id + '\n';
        if (item.location === 'extra') extra += id + '\n';
        if (item.location === 'side') side += id + '\n';
    }
});
```

Estructura del archivo .ydk:
#created by Destiny Draw
#main
[IDs del Main Deck, repetidos según cantidad]
#extra
[IDs del Extra Deck, repetidos según cantidad]
!side
[IDs del Side Deck, repetidos según cantidad]

1. ARQUITECTURA DEL MÓDULO DE ESTADÍSTICAS (estadisticas.js)
Se ha implementado el módulo Estadisticas bajo un patrón de objeto literal (Singleton), centralizando la lógica de análisis comparativo entre el deck del usuario y el "Meta".


Persistencia Local (LocalStorage): * El sistema utiliza la clave yugioh_meta_decks para almacenar toda la estructura de carpetas y decks sin necesidad de base de datos externa.


Por qué: Permite que el usuario mantenga su base de datos de consulta de forma privada y ultrarrápida.

Sistema de Carpetas Cronológicas:

Los decks se organizan en "Folders" (ej: "Febrero 2026").

Incluye lógica de ordenamiento por fecha (getMonthNumber) para que las carpetas más recientes aparezcan siempre primero.

2. MOTOR DE PROCESAMIENTO Y PARSING (YDK)
A diferencia del buscador que usa API, el módulo de estadísticas procesa archivos locales:


Parser de Archivos .ydk: Implementa parseYDK que limpia y extrae IDs de cartas directamente de archivos de texto del juego.


Identificación Automática de Miniaturas: * Función getMostFrequentCardId: Analiza el deck importado y determina cuál es la carta más repetida.


Cómo funciona: Este ID se usa para consultar automáticamente la imagen en los servidores de YGOPRODeck, asignando un arte representativo al deck de forma dinámica.

3. COMPONENTES DE INTERFAZ AVANZADOS (UI/UX)

Visualización de Scores Mediante Barras:

Se implementó un sistema de barras de progreso dinámicas (.stat-bar) con transiciones CSS para representar la Consistencia, Potencia y Resiliencia.

Utiliza colores variables (Dorado/Azul) para indicar la calidad del deck respecto al estándar de competición.

4. MEJORAS DE NAVEGACIÓN Y FEEDBACK

Fallback de Imágenes: Se implementó lógica de onerror en los thumbnails de los decks para mostrar una imagen por defecto (placeholder) si la API falla o la carta no existe, evitando "broken images" en la interfaz.

NOTAS TÉCNICAS ADICIONALES PARA PROGRAMADORES:

## 2. CAUSA RAÍZ

Los elementos `.widget-deck-item / .meta-deck-item` del widget:

* Son creados dinámicamente mediante `innerHTML`
* No poseen eventos `click` activos después del render
* No existe **delegación de eventos** en el contenedor padre

Cada re-render del widget elimina cualquier listener previamente asociado a los items.

---

## 3. DECISIÓN TÉCNICA

Se descartó:

* Uso de `onclick` inline
* Re-asignación de eventos por item tras cada render

Se adoptó:

* **Delegación de eventos** desde el contenedor del widget

Esta solución:

* Es persistente
* No depende del ciclo de render
* Escala correctamente con filtros, carpetas y futuros cambios

---

## 4. CAMBIOS IMPLEMENTADOS

### 4.1 Nuevo Listener Global del Widget

Se añadió un único listener `click` al contenedor `.deck-floating-widget`.

#### Función añadida

```js
Estadisticas.initFloatingDeckWidgetEvents()
```

Responsabilidades:

* Detectar clicks en cualquier deck renderizado
* Ignorar clicks en botones secundarios (eliminar)
* Extraer `data-deck-id`
* Delegar la acción de carga del deck

---

### 4.2 Lógica de Apertura / Sustitución de Deck

Se añadió / reemplazó la función responsable de cargar el deck desde el widget.

#### Función utilizada

```js
Estadisticas.openDeckFromWidget(deckId)
```

Responsabilidades:

* Buscar el deck seleccionado en `localStorage`
* Sustituir el deck activo (`Deck.cards`)
* Actualizar el nombre del deck (`Deck.name`)
* Renderizar el nuevo estado
* Marcar visualmente el deck activo

---

## 5. INTEGRACIÓN EN EL CICLO DE VIDA

La inicialización del listener se ejecuta:

* Una sola vez
* Después del render del widget
* Preferentemente desde `init()` o al final de `renderFloatingWidget()`

```js
Estadisticas.initFloatingDeckWidgetEvents();
```

Esto garantiza que:

* El listener no se duplique
* No se pierda tras futuros renders
