# DESTINY DRAW — REPORTE TÉCNICO
**Versión:** v2.9 | **Fecha:** Jul 2026 (auditado línea por línea contra el código fuente)
**Stack:** Vanilla JS (ES6 objects) · CSS modular · HTML5 SPA · YGOProDeck API · localStorage

> **Nota de auditoría:** este reporte fue verificado contra los 19 archivos fuente actuales.
> El footer de `index.html` marca **VERSION 6.4** — el número de versión de este documento
> (v2.9) es independiente y solo referencia la revisión del propio reporte.
> Cambio relevante desde la v2.8 (`mideck.js` — Optimización, ver 6.3, nuevo):
> 1. **Nuevo campo "Boardbreaker en mano"** en el formulario de Rondas de Duelo, ubicado
>    entre Handtraps y Bricks. Cuenta cartas que rompen campo jugando de segundo (Raigeki,
>    Dark Ruler No More, Evenly Matched, etc.). Se guarda como `round.boardbreakers`,
>    alimenta un promedio propio (`avgBoardbreaker`) y una sugerencia nueva en
>    `getOptDiagnostics()`. No afecta el cálculo de Brick Rate ni ningún otro campo.
> 2. **"Bricks en mano" renombrado a "Bricks/Tech en mano"** — cambio solo de rótulo visible;
>    a nivel de cálculo (Brick Rate, diagnósticos, export a Matchups) sigue considerándose
>    negativo/brick exactamente igual que antes, sin ningún campo o id nuevo.
>
> Cambios relevantes encontrados desde la v2.6 (`mideck.js` / `historial.js` — ver 6.1 y 6.2,
> nuevo, léelos antes de asumir el estado anterior):
> 1. **Complejidad del Deck** — nuevo clasificador de dificultad de uso/aprendizaje (quiz de
>    8 preguntas) dentro de Mi Deck → Optimización, con resultado también visible en
>    Construcción. Persiste en `complejidad_${deckName}`.
> 2. **Duelista ("Nivel como Piloto del Deck") reescrito por completo** — antes agregaba
>    duelos de TODOS los decks a lo largo de toda la vida de la app; ahora se calcula
>    EXCLUSIVAMENTE con las rondas de Optimización del deck activo, con una escala de
>    niveles reducida y nueva. Se renderiza en dos sitios (Estadísticas y Mi Deck →
>    Optimización) con el mismo contenido.
> 3. Los enfrentamientos de **Matchups** (Historial de Enfrentamientos) ahora son
>    clicables y filtran el "Historial de Sesiones" de Optimización por rival —
>    `Matchups.selectDeckFilter()` / `clearDeckFilter()`.
>
> El sistema G1/G2 Score sigue completamente implementado (ver 7.2, sin cambios desde v2.6).
>
> Cambios relevantes desde la v2.7 (`buscador.js` / `style_buscador.css` — CardViewer,
> ver 5.9, nuevo, léelos antes de asumir el estado anterior del panel "Ver"):
> 1. **Bloque de stats reordenado y renombrado** — orden ahora Nivel → Atributo → Tipo (antes
>    Atributo → Nivel, sin Tipo). El antiguo campo `card.type` (Effect Monster / Spell Card /
>    Trap Card…) ahora se rotula **"Carta:"**; el nuevo campo `card.type` **"Tipo:"** muestra
>    `card.race` (la Clase de monstruo — Dragón, Guerrero, etc.) y cae en "—" si la carta no
>    es monstruo. Evita la confusión histórica Tipo/Clase del juego.
> 2. **"Arquetipo:" añadido debajo de DEF** — enlace clicable (sin subrayado) que cierra el
>    CardViewer, cambia a la pestaña Buscador y ejecuta la búsqueda con ese arquetipo como
>    filtro activo, vía el nuevo `CardViewer.openArchetypeInBuscador()` (gemelo de
>    `openSetInBuscador`). Sin arquetipo → "—" sin enlace.
> 3. **"Lanzamiento TCG:" / "Lanzamiento OCG:" y "Disponible en:" (Master Duel / Duel Links)**
>    añadidos arriba de "📦 Pack / Set", poblados de forma async reutilizando el fetch
>    `misc=yes` que ya existía para los sets. "Disponible en:" solo se muestra si hay al
>    menos un formato; si no hay ninguno, la fila entera queda oculta.
> 4. **Bug corregido:** ese fetch leía `tcg_date`/`ocg_date`/`formats` en la raíz del objeto
>    de la carta, pero con `misc=yes` la API los anida dentro de `misc_info[0]`. Por eso
>    ninguna carta mostraba fecha ni disponibilidad. Ver bug #19 en sección 9.
> 5. **`ID:` del CardViewer ahora en `--gold-color`** (antes gris translúcido casi ilegible
>    sobre el fondo oscuro).

## 5. FLUJOS CRÍTICOS

### 5.1 Cambio de pestaña
```
switchTab(name) → Navigation.showTab(name)
  → oculta todos .tab-content, activa #name-content
  → Estadisticas.updateFloatingWidgetVisibility(tabName)
  → si simuladores:       Torneo.init()
  → si mideck:             Engines.init()
  → si saliendo de simuladores: ZonaPractica._cleanupFloatBtns()
  → si meta:               Meta.init()
  → si formacion:          Formacion.init()
  → window.scrollTo({ top:0, behavior:'smooth' })
  → ContentManager.applyAll()
```

### 5.2 Agregar carta al deck (desde Buscador)
```
Buscador.addCard(index)
  → Deck.syncFromViewer(card.id, card, currentQty + 1)
  → si carta nueva: autoAssignRoles() + SpecialtyAnalyzer + NomenclatureAnalyzer
  → Deck.render()  → recalcula Internal Score en tiempo real
    (Stats.calculateInternalScore — el mismo cálculo también actualiza g1Score/g2Score, ver 7.2)
  → External Score se recalcula si powerScoreCache existe
```

### 5.3 Importar .ydk a Mi Deck
```
Deck.importYDK()
  → input[file] .ydk → parseYDK(content, filename)
  → overlay de carga "Importando deck... N cartas"
  → fetch API YGOProDeck (batch por IDs únicos)
  → construye newCards con autoAssignRoles()
  → Deck.cards = newCards; Deck.render(); Deck.onDeckLoaded()
  → elimina overlay → alert "Deck importado"
```

### 5.4 Cálculo de scores — ciclo completo
```
Stats.calculateInternalScore(Deck.cards)
  → loop de roles → rendimientos decrecientes por pilar (consistency/power/resilience)
  → EN EL MISMO LOOP, por carta: calcula G1/G2 Score (ver fórmula completa en 7.2)
  → devuelve { internalScore, consistency, power, resilience,
               totalCards, mainCards, penalty, g1Score, g2Score }

Stats.calculateExternalScore(Deck.cards, powerScoreCache, metaDecks)
  → cruza specialties del deck con powerScoreCache
  → RPS modifier (ignorando loser='ninguno')
  → devuelve { externalScore, g1Vulnerability, g2Vulnerability, ... }
```

### 5.5 Actualizar Scores del Meta — flujo automático completo (async)
```
Estadisticas.recalculateAllMetaDeckScores()  ← async
  → lista todos los decks con secciones (sin importar si fueron abiertos antes)
  → crea overlay #meta-update-overlay con spinner + barra de progreso + nombre del deck actual

  FASE 1 (0–60%) Enriquecimiento automático:
    por cada deck en la lista:
      → IDs no presentes en metaCardLibrary → fetch API en batches de 10
      → autoAssignRoles() + SpecialtyAnalyzer para cada carta nueva
    → _saveMetaCardLibrary()

  FASE 2 (60–92%) Cálculo de scores:
    por cada deck:
      → _computeAndSaveMetaDeckScore(folder, filename)
      → Internal Score + pilares con fakeCards desde la librería

  FASE 3 (92–100%) Cross-Score N×N:
    → calculateCrossExternalScores()
    → metaDeckScores[key].externalScore = crossExternalScore
    → guarda yugioh_cross_scores + yugioh_meta_deck_scores

  → "¡Listo! N decks actualizados" 700ms → overlay desaparece → render()
```
Ya no es necesario abrir cada deck manualmente. Un solo clic procesa todos.

### 5.6 Selección de perfil
```
Welcome.enter(tabName, levelKey)
  → ContentManager.applyProfile(levelKey)  → 'dd_player_profile'
  → ConfigManager.savePlayerLevel(levelKey) → 'yugioh_player_level'
  → MusicPlayer.setTrack(cfg.tracks[levelKey])
  → Welcome.dismiss() → 'dd_welcome_dismissed' = 'true'
  → Navigation.showTab(tabName)
```

### 5.7 Borrar Todo / Restaurar Config
```
Config.borrarTodo()
  → localStorage.clear() + _resetModulesInMemory() + Welcome.init()

Config.resetToDefault()  ← parcheado por DefaultData
  → localStorage.clear() + await DefaultData.init()
```

### 5.8 DefaultData.init() — inyección única por tipo
```
window.load → DefaultData.init()
  → _initNotes / _initSpecialties / _initGames / _initMasters
  → _initDecks / _initStaples / _initEngines / _initGenesys  (fetch API)
  → _patchConfig() → sobreescribe Config.resetToDefault
```

### 5.9 Abrir CardViewer (panel "Ver" de carta) — NUEVO detalle documentado
```
CardViewer.open(card)
  → pinta overlay síncrono con lo que ya trae `card`:
      Carta: card.type (antes rotulado "Tipo:")
      Nivel → Atributo → Tipo (card.race; "—" si no es monstruo) → ATK → DEF
      Arquetipo: card.archetype como link, o "—" sin link si no tiene
      ID: card.id (en --gold-color)
  → fetch cardinfo.php?id=${card.id}&misc=yes (un único fetch, async)
      → card_sets  → rellena "📦 Pack / Set" (ya existía)
      → misc_info[0].tcg_date / ocg_date → "Lanzamiento TCG:" / "Lanzamiento OCG:"
        (fmtDate → toLocaleDateString('es-ES'); "No disponible" si falta)
      → misc_info[0].formats → "Disponible en:" (Master Duel / Duel Links).
        Fila oculta por completo si no hay match en ninguno de los dos.
  → click en Arquetipo → CardViewer.openArchetypeInBuscador(name)
      → cierra overlay → Navigation.showTab('buscador') → Buscador.clear()
      → Buscador._loadArchetypes() → advancedFilters.archetype = name → autoSearch()
      (mismo patrón que CardViewer.openSetInBuscador para sets)
```
**Importante:** `tcg_date`, `ocg_date` y `formats` SOLO existen dentro de `misc_info[0]`
cuando se pasa `misc=yes` — nunca en la raíz del objeto de la carta. Ver bug #19.

## 6. SUB-TABS Y SECCIONES

### Mi Deck
```
Sub-tabs: Decklist | Construcción | Optimización
Sidebar:  Engines | Decks | Staples | Favoritas

Optimización (🎯) — sub-tab de deck testing por matchup:
  → registra "rondas de duelo" con: orden (1º/2º), resultado, tipo de victoria/derrota,
    presión de tiempo, combo completo, starter, extenders, handtraps, boardbreaker en
    mano (ver 6.3), bricks/tech en mano, rompió board, negó jugada, rival rompió, notas.
  → agrupa rondas en "sesiones" (etiquetables: torneo, casual…), con badges de
    calidad (winrate, brick rate, % starters, consistencia de combo, score).
  → persiste en `optimization_${deckName}` vía Deck.getOptimizacion() /

  → migra automáticamente datos de un formato antiguo `records[]` a `sessions[]`.
```

### 6.1 Complejidad del Deck — NUEVO (clasificador de dificultad de uso/aprendizaje)

Quiz de 8 preguntas fijas (`Deck.CXD_PREGUNTAS`) repartidas en dos grupos de 4, cada
respuesta vale 1-3 puntos:

```
0-11   🟢 Ideal para empezar
12-15  🟢 Principiante
16-18  🟡 Intermedio
19-21  🟠 Avanzado
22-24  🔴 Experto
```

No se recalcula solo — el jugador debe re-evaluar manualmente si cambia el deck.

## 7. SISTEMA DE SCORING — DETALLE

### 7.1 Internal Score
`Stats.calculateInternalScore(cards)`. Loop de roles con rendimientos decrecientes.
Devuelve `{internalScore, consistency, power, resilience, totalCards, mainCards, penalty}`.

### 7.2 G1/G2 Score — IMPLEMENTADO Y CONECTADO (antes documentado como pendiente)

**Estado real verificado en el código (Jul 2026): la v2.5 de este reporte decía que esta
funcionalidad estaba "a medias" (config + UI sin motor de cálculo). Eso ya no es correcto —
el motor existe, se ejecuta en cada render de deck y se pinta en pantalla.**

Cálculo — dentro del mismo loop de `Stats.calculateInternalScore()` (`data.js`, dentro del
`for` sobre `cards`, dominio `loc === 'main'`):

```
Por cada carta (loc='main'):
  1. segments = NomenclatureAnalyzer.segmentDescription(rawDesc)
     → segmenta la descripción en categorías de nomenclatura
       (condicionActivacion, costoActivacion, restriccion, efectoGenerico...)

  2. layerMult = producto de L1 x L2 x L4 x L5
     por cada capa (layers = ConfigManager.getScoringLayers()):
       texto = segments[layer.nomenclatureCategory]
       busca la primera entry cuyo keyword aparezca en el texto
       multiplica por su .multiplier (si no matchea ninguna: x1.0)

  3. pool = qty de la carta
     + copias de cualquier Searcher en el main que mencione su nombre/arquetipo
       en su propia descripción (pool indirecto vía buscadores)

  4. reliability = ConfigManager.getReliability(pool)
     tabla por copias: 1→0.40, 2→0.65, 3→0.85, 4→0.90, 5→0.95 (config., default)

  5. por cada rol de la carta (item.roles):
       basePower = ConfigManager.getRoleBasePower(rol)      // L3, default 3
       cardScore = basePower x layerMult x reliability
       context   = ConfigManager.getRoleG1G2(rol)           // 'g1'|'g2'|'neutral'
       g1 → g1Score += cardScore
       g2 → g2Score += cardScore
       'neutral' → mitad y mitad (g1Score += cardScore*0.5, g2Score += cardScore*0.5)
```

`Stats.calculateInternalScore()` devuelve `g1Score` y `g2Score` (redondeados a 2 decimales)
junto al resto de campos ya documentados en 7.1.

**Clasificación G1/G2 por rol (default, `g1g2Roles` en `data.js`)** — coherente con el
metagame competitivo real: roles de apertura de mano/setup (`Starter`, `Extender`, `Booster`,
`Boss Monster`, `Tower`, `Token Summoner`, `Ignition`, familia `Stun-*`) → **g1**. Roles de
respuesta/interacción (`Handtrap`, `Boardbreaker`, `Disruptor`, `Removal`,
`Negate-activation`, `Negate-effect`, `Negater`, `Handloop`, `Speed-4`, `Anti-damage`) →
**g2**. El resto (`Searcher*`, `Recycler`, `Draw-engine`, `Protector`, etc.) → **neutral**.

**Renderizado** — `Estadisticas.renderDeckAnalysis()` (`estadisticas.js`):
- Bloque "Going First / Going Second" con `internalStats.g1Score` / `g2Score` en las clases
  `.analysis-g1g2-row/-item/-label/-val` — **ya no son huérfanas**, están en uso.
- `g1g2Profile`: frase de diagnóstico según proporción g1/g2 (diferencia >1.3x → "dependiente
  del dado" o "reactivo"; si no, "equilibrado") en `.analysis-g1g2-profile`.
- Si `analysis.hasPowerData && analysis.hasSpecData`, también muestra `g1Vulnerability` /
  `g2Vulnerability` (0-10), calculados en `Stats.calculateExternalScore()`.

**Detalle a tener en cuenta (no es un bug, es una decisión de diseño existente):**
`g1Vulnerability`/`g2Vulnerability` clasifican las **specialties/mecánicas** que counterean
al deck reutilizando `ConfigManager.getRoleG1G2()` — la misma tabla pensada para **roles**
de carta, no para nombres de mecánica. Si una specialty no coincide textualmente con una key
de `g1g2Roles`, `classify()` cae en `'neutral'` y esa amenaza no suma a ninguna de las dos
vulnerabilidades. Antes de tocar esta área, confirma con el usuario si quiere una tabla
G1/G2 separada para specialties o si reutilizar la de roles es intencional.

**Fórmula (ya implementada, no solo prevista):**
```
CardScore = BasePower(L3) x L1_mult x L2_mult x L4_mult x L5_mult x Reliability

L1 — Velocidad:   keywords en 'condicionActivacion'
L2 — Coste:       keywords en 'costoActivacion'
L4 — Restricción: keywords en 'restriccion'
L5 — Alcance:     keywords en 'efectoGenerico'
Reliability: tabla por copias (1→0.40, 2→0.65, 3→0.85, 4→0.90, 5→0.95)
             + pool indirecto de searchers del mismo arquetipo

g1g2Roles[dominantRole] === 'g1' → g1Score
g1g2Roles[dominantRole] === 'g2' → g2Score
'neutral'                        → 50/50
```

### 7.3 External Score (deck activo)
`Stats.calculateExternalScore()` — deck vs powerScoreCache.
RPS modifier ignorando loser='ninguno'.
Devuelve `{externalScore, g1Vulnerability, g2Vulnerability, ...}`.

### 7.4 External Score (meta) = Cross-Score N×N
`calculateCrossExternalScores()`. Para cada deck A: amenazas de counters de B ponderadas por internalScore de B y RPS. `crossExternalScore = (1 - threat/baseline) × 10`.

### 7.5 RPS
Reglas `[ganador, perdedor]`. `perdedor='ninguno'` → ese pilar no tiene counter. Modificadores: ×1.25 ventaja / ×0.75 desventaja / ×1.0 neutral.

```

```

### 8.2 Pattern de renombrado con input oculto (roles y nomenclatura)
El badge de nombre es siempre el elemento visible. El input se oculta con `display:none`.

| Elemento | Roles | Nomenclatura |
|---------|-------|-------------|
| Span visible | `id="rpn-${roleName}"` | `id="npn-${cat.id}"` |
| Input oculto | `id="rni-${roleName}"` | `id="nni-${cat.id}"` |
| Botón lápiz | `focusRenameInput(roleName)` | `focusNomRenameInput(catId)` |
| onblur | `renameRole(el)` | `renameNomCategory(catId, el)` |
| Clonar | `duplicateRole(roleName)` → `ConfigManager.duplicateRole` | `duplicateNomCategory(catId)` → `ConfigManager.duplicateNomenclatureCategory` |
| Borrar | `deleteRole(roleName)` | `deleteNomCategory(catId)` |

`duplicateNomenclatureCategory(catId)` — deep-copy de la categoría, nuevo ID `custom_` + timestamp, nombre + " (copia)", insertada inmediatamente después de la original. Devuelve el nuevo ID para scroll.
